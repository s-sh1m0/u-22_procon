### 1. ジョブ・解析結果に対するアクセス制御の欠如

| 項目 | 内容 |
|------|------|
| **危険度** | **9 / 10** |
| **分類** | 認可不備 (Broken Access Control) |
| **該当箇所** | `backend/internal/usecase/get_analysis.go`, `backend/internal/api/job_handler.go`, `backend/internal/api/diff_handler.go` |

**概要**: `GET /api/jobs/:id`, `GET /api/graph/:jobId`, `GET /api/diff/:jobId` は認証ユーザーであれば誰でも他ユーザーが作成したジョブの結果を取得できる。ジョブ ID（128-bit base64）の推測は現実的ではないが、URL 共有・ログ出力・ブラウザ履歴などで ID が漏洩した場合、プライベートリポジトリの diff やコールグラフが第三者に閲覧される。

**推奨対策**:
- `Job` エンティティに作成者（user ID / GitHub ユーザー名）を保持する
- usecase 層で取得時にリクエスト元ユーザーとジョブ所有者を照合する
- 不一致時は 403 Forbidden を返す

### 2. 任意リポジトリの clone + Go ツールチェーン実行（RCE リスク）

| 項目 | 内容 |
|------|------|
| **危険度** | **8 / 10** |
| **分類** | リモートコード実行 (Remote Code Execution) |
| **該当箇所** | `backend/internal/infra/job/worker.go:257` |

**概要**: 解析ワーカーはユーザーの OAuth トークンで任意の GitHub リポジトリを clone し、`go/packages.Load` を実行する。この処理は Go ツールチェーンを内部的に呼び出すため、悪意ある `go.mod`（`replace` ディレクティブ）、`//go:generate` タグ、または CGO を含むリポジトリを解析対象にされた場合、コンテナ内で任意コードが実行される可能性がある。コンテナが root で動作しているため、影響が拡大する。

**推奨対策**:
- コンテナを非 root ユーザーで実行する（後述 #6）
- 解析をネットワーク分離されたサンドボックスコンテナで実行する
- `CGO_ENABLED=0` を解析実行時の環境変数としても明示設定する
- clone 後に `go.mod` の `replace` ディレクティブを検証する

### 3. CSRF 対策の欠如

| 項目 | 内容 |
|------|------|
| **危険度** | **8 / 10** |
| **分類** | クロスサイトリクエストフォージェリ (CSRF) |
| **該当箇所** | `backend/internal/api/router.go:42`, `backend/internal/api/auth_handler.go:140`, `frontend/src/lib/api.ts:24` |

**概要**: `POST /api/analyze` および `POST /auth/logout` に CSRF トークンの検証がない。クロスオリジン構成（`FRONTEND_URL` 設定時）ではセッション Cookie が `SameSite=None` に設定されるため、攻撃者のサイトから被害者の GitHub トークンを使った解析リクエストが送信可能になる。同一オリジン構成でも `SameSite=Lax` は GET リクエストでの CSRF を防げるが POST には不十分なブラウザ実装が存在する。

**推奨対策**:
- Double-Submit Cookie パターンまたは Synchronizer Token パターンで CSRF トークンを導入する
- フロントエンドの API クライアントにトークンヘッダーを追加する
- `Origin` / `Referer` ヘッダーのサーバー側検証を追加する

### 4. レート制限の欠如

| 項目 | 内容 |
|------|------|
| **危険度** | **7 / 10** |
| **分類** | サービス拒否 (DoS) |
| **該当箇所** | `backend/internal/api/router.go` |

**概要**: `POST /api/analyze` にユーザー単位・グローバルともにレート制限がない。各リクエストはリポジトリの git clone + 完全な AST/SSA 解析という高コストなジョブをエンキューする。単一ユーザーが大量のリクエストを送信することで、メモリ上限（5GB）の枯渇やジョブキューの飽和を引き起こせる。

**推奨対策**:
- Echo の `middleware.RateLimiter` を導入する（例: ユーザーあたり 5 req/min）
- usecase 層でユーザーあたりの同時実行ジョブ数を制限する
- キュー満杯時に 503 Service Unavailable を即座に返す（後述 #5）

### 5. ジョブキューの Enqueue がブロッキングでデッドロックの可能性

| 項目 | 内容 |
|------|------|
| **危険度** | **7 / 10** |
| **分類** | サービス拒否 (DoS) / デッドロック |
| **該当箇所** | `backend/internal/infra/job/queue.go:23` |

**概要**: `Enqueue()` はバッファ付きチャネル（デフォルト 32 スロット）への送信でブロックする。HTTP ハンドラの goroutine 内で呼ばれるため、キューが満杯になると後続のリクエストが無期限にハングし、サーバー全体が応答不能になる。

**推奨対策**:
- `select` + `default` による非ブロッキング送信に変更する
- キュー満杯時はクライアントに 503 を返す
- タイムアウト付き `select`（`context.Context` 利用）も代替案

### 6. 本番コンテナが root で実行されている

| 項目 | 内容 |
|------|------|
| **危険度** | **7 / 10** |
| **分類** | コンテナセキュリティ |
| **該当箇所** | `backend/Dockerfile:9`, `Dockerfile.prod:19` |

**概要**: いずれの Dockerfile にも `USER` ディレクティブがなく、コンテナ内のプロセスが root 権限で動作する。前述の RCE 脆弱性（#2）と組み合わさった場合、攻撃者がコンテナ内で root 権限を取得し、ボリュームマウントされた DB ファイルや環境変数（SESSION_SECRET 含む）にアクセスできる。

**推奨対策**:
```dockerfile
RUN useradd -r -s /usr/sbin/nologin appuser
RUN chown -R appuser:appuser /app /app/data
USER appuser
```

### 7. セッションのサーバー側有効期限がない

| 項目 | 内容 |
|------|------|
| **危険度** | **6 / 10** |
| **分類** | セッション管理不備 |
| **該当箇所** | `backend/internal/infra/store/session_repo.go` |

**概要**: セッション Cookie には 7 日間の `MaxAge` が設定されているが、DB 上のセッションレコードには有効期限がない。Cookie が窃取された場合（XSS、ネットワーク盗聴など）、そのセッション ID は DB レコードが削除されない限り永久に有効。ユーザーがログアウトしても、窃取済みの Cookie は引き続き使用できる可能性がある。

**推奨対策**:
- セッションテーブルに `created_at` / `expires_at` カラムを追加する
- `FindByID` で有効期限チェックを行う
- 定期的な期限切れセッション削除ジョブを実装する
- ログアウト時にサーバー側セッションレコードを確実に削除する

### 8. セキュリティレスポンスヘッダーの欠如

| 項目 | 内容 |
|------|------|
| **危険度** | **6 / 10** |
| **分類** | ヘッダー設定不備 |
| **該当箇所** | `backend/internal/api/router.go` |

**概要**: 以下のセキュリティヘッダーが一切設定されていない:
- `X-Content-Type-Options: nosniff`
- `X-Frame-Options: DENY`
- `Content-Security-Policy`
- `Strict-Transport-Security`（HTTPS 運用時）
- `Referrer-Policy: strict-origin-when-cross-origin`

クリックジャッキング、MIME スニッフィング、意図しないフレーム埋め込みなどのリスクがある。

**推奨対策**:
- Echo の `middleware.Secure()` を追加するか、カスタムミドルウェアで一括設定する
- フロントエンドにも CSP の `<meta>` タグを追加する

### 9. 暗号鍵導出が脆弱

| 項目 | 内容 |
|------|------|
| **危険度** | **5 / 10** |
| **分類** | 暗号実装の脆弱性 |
| **該当箇所** | `backend/internal/infra/store/session_repo.go:26` |

**概要**: `SESSION_SECRET` から AES 暗号鍵を導出する際、SHA-256 を 1 回適用するだけで使用している。SESSION_SECRET が短い・予測可能な文字列（例: `.env.example` の `change_this_to_random_string`）の場合、DB を取得した攻撃者がブルートフォースで鍵を復元し、保存された OAuth トークンを復号できる。

**推奨対策**:
- PBKDF2、Argon2、または scrypt による鍵導出に変更する
- `SESSION_SECRET` の最低長（32 バイト以上のランダム文字列）をバリデーションする
- `setup.sh` でランダム生成を強制する

### 10. 内部エラー情報のクライアントへの漏洩

| 項目 | 内容 |
|------|------|
| **危険度** | **5 / 10** |
| **分類** | 情報漏洩 (Information Disclosure) |
| **該当箇所** | `backend/internal/api/middleware.go:25`, `auth_handler.go:73,77,91`, `analysis_handler.go:68,104`, `job_handler.go:31`, `diff_handler.go:46`, `frontend/src/pages/Analysis.tsx:49` |

**概要**: Go のエラーチェーンがそのまま HTTP レスポンスに含まれており、DB ファイルパス、GitHub API の URL、ネットワークエラーの詳細などが外部に露出する。フロントエンドでもバックエンドから受け取ったエラー文字列をそのまま表示している。

**推奨対策**:
- サーバー側: 詳細エラーはログに出力し、クライアントにはジェネリックメッセージのみ返す
- フロントエンド側: 未知のエラーは一律「予期しないエラーが発生しました」などに変換する

### 11. OAuth トークンがメモリ上に平文で保持される

| 項目 | 内容 |
|------|------|
| **危険度** | **5 / 10** |
| **分類** | 機密データの取り扱い |
| **該当箇所** | `backend/internal/infra/github/client.go:18` |

**概要**: GitHub の OAuth トークンがマップキーとして平文でメモリに保持される。メモリダンプやコアダンプでトークンが漏洩する可能性がある。また、キャッシュが 64 エントリに達すると全消去（thundering herd）される設計で、一時的な負荷集中を引き起こす。

**推奨対策**:
- トークンのハッシュ値をマップキーにする
- LRU キャッシュに置き換えて段階的に eviction する

---

### 12. フロントエンドの認証キャッシュが無期限

| 項目 | 内容 |
|------|------|
| **危険度** | **4 / 10** |
| **分類** | 認証状態管理 |
| **該当箇所** | `frontend/src/hooks/useAuth.ts:9` |

**概要**: `useAuth` フックの `staleTime: Infinity` 設定により、一度認証されるとサーバーへの再検証が行われない。セッションが期限切れやサーバー側で無効化されても、ブラウザ上では認証済みの状態が維持される（ゴースト認証）。

**推奨対策**:
- `staleTime` を有限値（例: 5 分）に設定する
- API クライアントに 401 レスポンスのインターセプターを追加し、認証キャッシュを無効化する

### 14. GitHub リンク生成時の URL エンコード不足

| 項目 | 内容 |
|------|------|
| **危険度** | **4 / 10** |
| **分類** | URL インジェクション |
| **該当箇所** | `frontend/src/lib/githubLinks.ts:21` |

**概要**: `pr.owner`, `pr.repo`, `ref` が URL エンコードなしで GitHub blob URL に埋め込まれる。バックエンドからの応答が改ざんされた場合、`github.com` 外のサイトへのリンクが生成される可能性がある。

### 15. DB と復号鍵が同一コンテナ内に共存

| 項目 | 内容 |
|------|------|
| **危険度** | **4 / 10** |
| **分類** | シークレット管理 |
| **該当箇所** | `compose.yml:33`, `compose.prod.yml:10-14` |

**概要**: SQLite DB（暗号化されたトークンを含む）と `SESSION_SECRET`（復号鍵の導出元）が同一コンテナ内に存在する。コンテナが侵害された場合、暗号文と鍵の両方が同時に漏洩する。

### 20. CI/CD パイプラインにセキュリティスキャンがない

| 項目 | 内容 |
|------|------|
| **危険度** | **2 / 10** |
| **分類** | DevSecOps |
| **該当箇所** | `.github/workflows/frontend-lint.yml`, `.github/workflows/backend-lint.yml` |

**概要**: CI では lint / 型チェック / フォーマットのみ実行され、以下のセキュリティチェックが欠如している:

- Trivy / Snyk 等のコンテナスキャンを追加する

## 良い点（ポジティブ所見）

- `dangerouslySetInnerHTML`, `innerHTML`, `eval()` の使用なし（XSS 耐性が高い）
- localStorage / sessionStorage に機密情報を保存していない
- セッション管理は httpOnly Cookie を使用（クライアント側トークン不使用）
- 外部リンクに `rel="noreferrer"` / `rel="noopener noreferrer"` を適用
- PR URL 入力は `parsePrUrl()` で GitHub URL パターンに厳密にバリデーション
- `.env` が `.gitignore` に含まれている
- OAuth state パラメーターで CSRF 対策を実施（OAuth フロー自体）
- メモリ上限（`GOMEMLIMIT`, `mem_limit`）による OOM 対策
- ジョブタイムアウトによる暴走防止
